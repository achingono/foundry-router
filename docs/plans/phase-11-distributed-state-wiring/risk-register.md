# Phase 11 Risk Register

## Risks

| ID | Risk | Impact | Mitigation | Status |
|---|---|---|---|---|
| R1 | `sync_from_settings` unconditionally upserts the balance row with zero reservations and the initial remaining balance (`state/table.py:313-340`, `:896`), so every scale-out or restart resets shared credit. | Credit oversubscription across replicas | Create-if-absent sync with an ETag-guarded config-only merge; unit and Azurite tests that start a second instance against a populated store | Open |
| R2 | Fail-closed semantics (ADR-005) turn a storage outage or throttling into a full router outage. | Availability | Bounded timeouts; readiness check; storage-outage runbook; documented as intended; throttling alert if the step-16 estimate warrants it | Open |
| R3 | RBAC propagation lags the first deployment, so early requests get 403 and replicas look unhealthy. | Flaky first deploy, false alarms | Readiness recovers without restart; first-deploy convergence verified and documented as for Phase 10 R5 | Open |
| R4 | Per-backend partitions concentrate all replicas' reservations on one partition, raising ETag conflict and retry rates under load. | Latency, spurious capacity rejections | Existing bounded retries; measure the conflict rate in step 15; record partition throughput versus measured request rate | Open |
| R5 | Every routed request adds Table round trips (reserve, settle) to the hot path. | Latency and transaction cost | Record per-request transaction count and cost; keep the existing short-TTL balance cache for reads; Redis stays out of scope per ADR-005 | Open |
| R6 | Per-replica in-memory rate-limit accounting lets aggregate traffic exceed provider quota once replicas exceed one. | Provider 429s, cooldown churn | D6 option B through one effective-limit contract, so routing and admin re-syncs cannot revert the share; zero-share readiness check; protected-fallback (D7) and rollout-overlap exemptions documented and tested | Open |
| R7 | An `existing` Storage account still permits shared-key access or is shared with other workloads. | Weaker authentication posture, cross-workload blast radius | Never mutate attached accounts; namespaced table prefix; table-scoped role assignment; document the posture difference | Open |
| R8 | Changing store construction from module globals to a lifespan factory breaks tests that monkeypatch the globals. | Large test churn | Preserve attribute names or update the affected tests in the same change; default backend remains `memory` | Open |
| R9 | A storage key, SAS token or connection string reaches the repository through test fixtures or local overrides. | Credential exposure | Azurite fixture credentials stay in `tests/` only; gitignored `*.local.json`; final diff scan | Open |
| R10 | Documentation is relabelled `Implemented` before the two-replica deployment is proven. | Repeats the gap this phase closes | Exit criteria tie every label change and the prod parameter change to the step-15 deployment evidence | Open |
| R11 | The async SDK returns ETags in `entity.metadata`, not the `"odata.etag"` key the adapter reads (`state/table.py:988`), so balance writes would go out unconditional. | Silent lost updates; credit oversubscription | Client normalises ETags; balance `Update`/`Delete` without an ETag raises; tests use real SDK types and Azurite | Open |
| R12 | Settle and reaper retries resend a balance computed before the competing write (`state/table.py:613-628`, `:846-862`), and retries inside the cache TTL re-read the same stale ETag. | Lost reservations or debits; spurious retry exhaustion | Recompute from fresh storage reads on every conflict; invalidate the cache on failure; no write fed from the cache; interleaving tests | Open |
| R13 | `maxReplicas` bounds one revision; a rollout briefly runs old and new revisions together, including a memory-backed revision during cut-over. | Split credit state during cut-over; brief rate-limit overshoot | Single-revision mode; cut-over runbook deploys `table` at one replica and confirms no memory-backed revision serves traffic before scaling; overshoot documented | Open |
| R14 | Cut-over from `memory` cannot carry in-memory spend or reservations, so the Table store starts from configured initial balances. | Credit over-estimate immediately after cut-over | Reconcile `backend_initial_estimated_remaining_usd` before cut-over; recorded go decision; rollback retains Table data | Open |
| R15 | Tables and role assignments for an `existing` account in another resource group cannot deploy from a group-scoped template, and the deployer may lack rights there. | Failed deployment in `existing` mode | Module scoped to the storage resource group; documented deployer permissions; cross-group validation gate | Open |

## Decisions

- **D1 — The template provisions the tables; the app never creates them.** This keeps the identity at data-plane entity access, avoids startup races between replicas, and makes a missing table a readiness failure rather than silent creation.
- **D2 — Identity-only authentication.** Use `ManagedIdentityCredential` in Container Apps and `DefaultAzureCredential` only for local developer runs. No shared-key, SAS or connection-string path exists in `src/`; Azurite credentials are test-only.
- **D3 — Role scope is per table.** `Storage Table Data Contributor` is assigned on each router table, not the account, so an attached shared account exposes only the router's tables.
- **D4 — `stateBackend` defaults to `memory`, and `maxReplicas > 1` requires `table`.** This keeps CI validation hermetic and makes the split-brain configuration unrepresentable in the template.
- **D5 — Separate health and credit tables.** The consistency models differ (last-write-wins versus ETag transactions), and separate tables keep diagnostics and role scope clear while preserving the ADR-005 per-backend partition layout.
- **D6 — Rate-limit state across replicas. Decided by the maintainer: Option B.**
  - *A — Table-backed counters:* fixed-window counters per quota group (minute buckets for RPM/TPM, a Pacific-date row for RPD) with ETag increments. Exact aggregate enforcement, but it changes Phase 09 sliding-window semantics and adds hot-path I/O. Deferred as a future option if measured underuse from B justifies it.
  - *B — Per-replica share (selected):* keep `InMemoryRateLimitStore` and enforce `floor(limit / maxReplicas)` per replica. Never exceeds provider quota, needs no new I/O, but underuses quota when traffic is skewed.
  - *C — Accept over-limit and rely on provider 429 cooldown.* Rejected: it violates the Phase 09 intent of avoiding provider throttling.
- **D7 — Protected emergency fallback stays exempt from the per-replica share. Proposed; needs maintainer confirmation.** The fallback already bypasses quota by design (`allow_over_limit=True`, `routing/__init__.py:391`). Keeping it exempt preserves Phase 09 behaviour. Its admissions still count toward the replica's usage, and the D6 guarantee is stated as applying to ordinary admissions only. The alternative, disabling the fallback for quota-managed groups whenever `maxReplicas > 1`, would be a routing behaviour change and needs its own decision.
