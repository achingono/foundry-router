# Phase 08 Risk Register

## Risks

| ID | Risk | Impact | Mitigation | Status |
| --- | --- | --- | --- | --- |
| R1 | F1 change misses a code path that still uses the client correlation ID as the reservation key | Credit accounting remains corruptible | Trace the identity end to end (route → routing → credit → streaming); add the concurrent duplicate-ID regression test as the gate | Mitigated — server-owned reservation key traced through routing/credit/streaming; the concurrent duplicate `x-request-id` regression test in `tests/unit/test_main.py` passes (exit criteria F1) |
| R2 | Body-size limit set too low breaks legitimate large but valid requests | False `413` rejections | Choose a generous default, make it configurable, and document it; test a just-under-limit valid body | Mitigated — `max_request_body_bytes` defaults to 2 MiB, is configurable via `FOUNDRY_MAX_REQUEST_BODY_BYTES`, and is documented in `docs/configuration/index.md` (exit criteria F2) |
| R3 | F3 hard config-load failure is too strict for partial local testing | Blocks developers running subsets locally | Decide between fail-fast config validation and a readiness check; record the decision; prefer readiness if partial local runs are required | Resolved: implemented as a `/health/ready` check (`backend_credit_config_complete`, `model_pricing_complete`) rather than a config-load failure, since a hard failure made the existing request-time fail-closed defense unreachable and broke legitimate partial-configuration test scenarios |
| R4 | Reservation reaper reclaims a still-inflight streaming request that legitimately runs long | Premature credit release and possible double accounting | Set max age to backend timeout plus margin; only reap strictly older reservations; add a long-running-stream test that is not reaped | Resolved: default `reservation_max_age_seconds` is 900s (well above the 60s backend client timeout plus retry/streaming margin); the sweep only reaps strictly-older reservations under the existing lock; `test_long_running_stream_reservation_not_reaped_when_within_max_age` and `test_fresh_reservation_is_untouched_by_reaper` cover this |
| R5 | Removing per-request `sync_from_settings` (F6) breaks a test that relied on its side effect | Test regressions | Confirm startup/lifespan sync covers the need; update tests to not depend on per-request sync | Resolved: the per-request call was retained (removing it broke 20+ existing tests and any caller that swaps the `Settings` singleton without an explicit sync); a settings-object-identity fast path was added instead so repeated calls with the same `lru_cache`d settings instance are effectively free |
| R6 | F7 pre-filter accidentally skips a valid usage event with unusual formatting | Under-charged streaming cost | Pre-filter on a substring guaranteed present in usage events; keep full parse when the guard matches; test terminal usage extraction | Resolved: the pre-filter checks for the literal `b"usage"` substring in the raw SSE event payload before any line-splitting or JSON parsing; existing terminal-usage tests continue to pass unchanged |
| R7 | Documentation drifts ahead of implementation (present-tense claims) | Violates repository status-labelling rule | Update docs only after verification; use the four status labels consistently | Resolved: traceability, security, observability, and configuration docs were updated only after the full test suite, lint, and type checks passed |

## Open Decisions
- F3 enforcement location: **Decided** — reported at `/health/ready` (`backend_credit_config_complete`, `model_pricing_complete`) rather than fail-fast at config load, to preserve the existing request-time fail-closed defense and legitimate partial-configuration test scenarios.
- Whether to expose oldest-reservation age (not only count) in `/admin/status`: **Decided** — yes; computed in the same locked pass as reservation counts in `live_snapshot`, so it adds no extra lock acquisition.
- Default values for `max_request_body_bytes` and `reservation_max_age_seconds`: **Decided** — `max_request_body_bytes` defaults to 2,097,152 bytes (2 MiB); `reservation_max_age_seconds` defaults to 900 seconds, well above the 60-second backend client timeout plus retry/streaming margin.
- F6 scope: **Decided** — the per-request `sync_from_settings` call was retained (not removed) because removing it broke correctness for callers that swap the `Settings` singleton without an explicit sync; a settings-object-identity fast path makes repeated calls with the same instance effectively free instead.
