## Original Major findings and resolution

The issue descriptions below record the original review. Resolution is documentary; no runtime fix or acceptance result is asserted.

### M1 — Leave provider semantic/token-limit validation upstream

- **Status: Resolved.** Amended bottom line (line 13), direction steps 3–4 (67–68), and regression bullets (78–79, 83) explicitly leave exact token/context validity upstream. They prohibit mandatory tokenizers, token-count calls, token-array feature expansion and exact local token-boundary rejection tests. Existing conservative estimation, missing-pricing failure, MAI liability and settlement are retained. Consuming mocks exercise upstream semantic-error handling without paid validation probes. This closes M1's scope and false-rejection concern at the research level.

- **Location:** Research implementation direction steps 3–4; embeddings and Anthropic/MAI benchmark bullets (original lines 67–79).
- **Issue:** “Keep ... values as token checks,” the tokenizer requirement, and exact token-boundary validation tests turn byte-cap remediation into a new provider-validation subsystem. An approximate financial estimator cannot decide exact upstream token validity. This is especially problematic when model/tokenizer versions differ or MAI's tokenizer is unspecified.
- **Impact:** Valid Foundry requests could acquire new local rejection paths; implementation scope and dependencies expand beyond the allocation router's size problem.
- **Required correction:** Record the provider token limits as research facts and benchmark context. Keep provider context/token-limit semantics upstream-owned. Preserve existing conservative financial estimation, pricing failure behavior, output liability and settlement; do not mandate a tokenizer, token-count API call, exact provider token prevalidation, new input form, or model capability. A tokenizer used solely to generate an offline fixture is optional and does not authorize runtime enforcement. Tests should prove size handling, estimator parity and faithful upstream-error handling with a mock rather than require local rejection at 8,193 or 300,001 tokens.

### M2 — Prove capacity supports ordinary upstream-supported representations

- **Status: Resolved.** Amended bottom line (line 13), direction step 6 (70), benchmark bullet (82), and final status (85) make idle single-request capability mandatory and distinct from concurrent overload. The complete local path must consume near-512-MB content plus Base64/JSON overhead, near-50-MB PDFs, normal escaping/Unicode, model-last chunking and supported text above old adapter caps. An idle failure due to memory, spool, estimator/work or deadline limits is explicitly an unresolved undersized design, not a passing busy outcome. Concurrent busy acceptance follows idle success; the ≤70% aggregate memory target, scratch headroom, readiness and cleanup remain required. Unknown wire maxima do not become unlimited support claims. This closes M2's policy-cap loophole in the future acceptance criteria; benchmarks remain outstanding.

- **Location:** Research bottom line and implementation direction step 6 (original lines 13 and 70); Phase 4 benchmark acceptance.
- **Issue:** The research correctly warns about finite resources, but makes a sufficiently large lane conditional on a product intent to accept maxima “regardless of instantaneous resource pressure.” That conflates baseline capability with availability under load. The user already requires supported Foundry sizes. A single ordinary supported request that always fails on an otherwise idle replica is a lower effective size cap even if its response is called 503/busy.
- **Impact:** A small fixed spool, memory budget, parser-work ceiling, or deadline could recreate the rejected 413 policy in disguise.
- **Required correction:** Make idle-lane capability and concurrent-overload behavior separate mandatory acceptance cases. Benchmark the selected final Linux container/resource pair through intake, parsing, estimation, rewrite and mocked upstream consumption for ordinary supported representations, including near-512-MB image content plus Base64/JSON overhead, near-50-MB PDFs, Unicode/normal escaping, model-last chunking and supported text translations above old adapter byte caps. No obsolete downstream estimator/adapter/work limit may defeat these cases. Busy rejection is acceptable for genuine finite capacity contention only after this support is demonstrated. Retain the ≤70% aggregate memory target, measured scratch headroom, readiness and cleanup requirements. An idle-capacity failure is an unresolved architecture gap, not successful payload support.
- **Unknown maxima:** Do not manufacture a finite Azure wire maximum or promise all possible padding/metadata encodings. Select a measured service envelope that supports ordinary representations of documented supported content; state residual unknowns. If that cannot be achieved within the smallest safe design, record the blocker for an explicit decision. Renaming a fixed lower policy ceiling is insufficient.

## Original suggestions and remaining design gaps

The numbered suggestions below are retained as the original review record. Current disposition:

- **Suggestions 1, 2 and 5 addressed:** lines 13, 65, 67–69 and 77–83 prioritize measurement before complexity, use format-valid generated media and consuming mocks, separate malformed fixtures, prohibit paid synthetic/giant acceptance probes, and keep upstream semantic ownership explicit.
- **Suggestion 6's wording correction addressed:** lines 10, 19 and 28 now quote the PDF aggregate as a 50 MB combined limit without claiming an explicitly strict-under aggregate rule. Selected resources, mechanism details and measured results remain future G3 work, as intended.
- **Suggestions 3 and 4 remain implementation handoff considerations, not research blockers:** the v1-versus-deployment-scoped embeddings distinction remains explicit; no route migration/token-array expansion is authorized. Preserve shared-adapter and mixed-pool/non-Azure behavior when implementing the Azure-local change.
- **Minor editorial follow-up:** direction step 2 (line 66) and the capacity/lifecycle bullet (81) still phrase spool reservation/files/disk-error cases unconditionally. Read them as applicable only if the benchmark selects spooling, consistent with the explicit alternatives in lines 13, 65, 68–69 and 82. Qualifying them with “if spooling is selected” would improve consistency; they do not require a spool or new infrastructure and do not reopen M1/M2.

1. **Keep the design choice open until measured.** The research's bottom line prematurely favors an incremental parser plus spool, whereas [Phase 4 step 21](activities.md#phase-4--azure-operation-payload-contract-and-simplest-safe-resource-architecture) explicitly starts with the smallest benchmarked safe option. A finite admitted in-memory path is eligible only if actual amplification, aggregate capacity and supported ordinary representations fit; `cap=None` plus unbounded whole-body parsing is ineligible. Use private quota-accounted ephemeral spooling/incremental rewriting where measurements require it. No new gateway, storage service, collector or environment is justified by this research alone.
2. **Make synthetic fixture claims precise.** The existing “provider egress blocked” requirement is good. PDF-like bytes and arbitrary Base64 are useful transport-load fixtures but do not prove valid PDF/image support and can be rejected before exercising the expensive path. Use generated format-valid representative media and a consuming mock where the real local path needs it; retain invalid fixtures as explicitly negative cases. Near-boundary decimal/MiB fixtures probe engineering headroom, not undocumented Azure acceptance. Do not send fake PDF/image fixtures to paid inference, require paid giant requests, or label local mock success Azure acceptance.
3. **Bind endpoint/version facts before implementation.** The cited embeddings guide/reference concern v1; the current router uses a deployment-scoped versioned route. The research discloses this correctly but does not establish exact deployed-version equivalence. Keep that distinction and verify the applicable Microsoft contract if a later design depends on exact endpoint-specific behavior; do not silently migrate routes or add token-array support. Current `request_body` accepts embedding string inputs/string lists, not the full v1 token-array schema. This is a capability boundary, not a reason to expand this size task.
4. **Preserve shared-adapter boundaries.** The 256 KiB/128-item/128-part Anthropic intake bounds originate in inherited `compatible_text.py`; that code also serves preserved providers. Keep the Azure-specific change provider-local. Model-last handling must resolve candidate backends server-side, including mixed pools/failover, without granting non-Azure backends larger effective limits. Non-Azure configuration, prices, funds and capability policy retain their already-approved scope; no re-review of their upstream contracts or live calls is required here.
5. **Clarify ownership of source limits.** “Apply the Azure operation-specific contract” should not imply recreating every upstream feature/schema/media validator. Keep essential routing, authentication, safe syntax/resource handling and financial estimation local. Provider-specific semantic validity remains upstream-owned. Published size limits alone do not mandate media decoding, tokenizer implementation, Anthropic media/stream support or MAI edits.
6. **Separate research completion from G3 completion.** A selected static pair, actual parser/writer strategy, aggregate memory/spool admission weights, resource lifetimes, end-to-end deadline viability and benchmark results are still absent by design. These are future design/acceptance evidence, not errors in the sourced limits. Correct the PDF aggregate wording noted above and retain explicitly unknown Azure wire bounds.
