### Phase 4 — Azure operation payload contract and simplest safe resource architecture

Research may proceed read-only alongside earlier phases; implementation/deployment follows independent contract approval. Payload changes do not block a safe Table/one migration, but block final payload/autoscaling completion.

19. Build a dated source-backed matrix for each enabled Azure operation/model: Azure OpenAI Responses text/tools/images/files, deployment-scoped embeddings, Foundry Anthropic Messages translation and MAI image generation. Record decoded prompt/image/file bounds, wire limits (known or **unknown**), context/output limits and route/API version separately. Inspect platform ingress request size/time/chunking limits and supported CPU/memory pairs. Do not import public Anthropic/OpenAI/non-Azure or Google quota semantics into Azure operations without Azure evidence.
20. Honor the user's rejection of router caps below supported upstream payloads. Responses' documented combined prompt/images <512 MB is a content constraint, not automatically `max_request_body_bytes=512*1024*1024`; base64, JSON escaping and metadata can make wire size larger. Resolve units/serialization and upstream-owned wire policy before hard-coding any numeric wire ceiling. Embeddings and Azure Anthropic/MAI need their own sources; current 256 KiB/64 KiB translation bounds or image inspection limits are local constraints, not proven upstream maxima. Unsupported capabilities remain separately scoped, but size restrictions on supported operations cannot silently remain below upstream support.
21. Preferred smallest safe design: operation/provider-owned intake policy, authenticated bounded-resource admission **before** body intake, nonqueued weighted aggregate capacity, finite deadlines and bounded incremental parsing/serialization/forwarding. Benchmark first to choose whether one admitted large request can safely use bounded in-memory parsing in a larger static container. If copies/objects exceed safe supported sizing, use bounded private ephemeral spooling plus incremental parsing/model substitution/cost walking/outbound serialization; no full unbounded `request.body()`/`json.dumps` chain, no `cap=None` with whole-body buffering. Disk also needs byte/capacity accounting, isolation and cancellation cleanup. Unknown wire limits remain upstream-owned; router overload/time/security rejections must be accurately classified, not disguised arbitrary per-request 413 caps.
22. Close the chicken-and-egg routing issue: model may appear last in JSON and Content-Length may be absent/false. Admit intake under a safe resource policy before parsing, resolve aliases/pools without trusting caller provider selection, then enforce the operation's documented policy; preserve other providers' existing caps/translation behavior even when the common intake path supports larger Azure requests. If a finite physical-storage architecture cannot safely support unknown wire size without imposing a rejected product cap, record blocker and obtain independent architecture/user decision rather than claiming unlimited support.
23. Preserve constant-time auth before expensive work, allow-listed HTTPS egress, duplicate/nonfinite/depth/work protections, no request decompression bombs, bounded parser tasks/queues, cancellation/slow-client time limits and redacted logging. Structural work protection must accommodate ordinary upstream-supported payload shapes; arbitrary fixed node ceilings cannot quietly become a lower payload cap. Release resources on every error/cancellation with no free financial release after possible dispatch.
24. Preserve deployed estimator corrections: accepted Azure bodies must not hit an obsolete independent size/serialization ceiling; charge all applicable input/instructions/tools/schema/media according to existing configured financial policy. Streaming/incremental estimates must match current conservative results and distinguish caller invalidity from missing price. No token-to-byte equivalence, unlimited credit, zero-cost media inference or swallowed estimation failures. Preserve SSE bytes/event boundaries, deadlines and no retry/failover after meaningful output.
25. Benchmark generated synthetic fixtures with provider egress blocked: near/at supported decoded content boundary with realistic base64/JSON overhead, Unicode/escaping/tools, model-last/chunked intake, maximum structural shapes, concurrent small+large requests, disconnect/slow upload and slow downstream stream. Measure actual wire bytes, peak RSS/container memory, CPU/event-loop/health latency, disk if used, scratch copies and cleanup. Require peak aggregate memory ≤70% of selected static container memory, readiness responsiveness during admitted workload, no OOM/leaks after repeated cycles and deterministic bounded overload before memory exhaustion. Choose an Azure-supported static resource pair from results; 0.25/0.5 GiB is not presumptively sufficient. Paid giant-payload inference is not necessary for memory benchmarking and is not included in USD 1 small-call acceptance.

### Phase 5 — Shared admission and observability prerequisite acceptance

Depends on Table/one acceptance and approved payload/resource design. Scale remains one until this gate closes.

26. Audit actual quota policies and owning groups per preserved provider/model/deployment. Current Table quota implementation uses input-TPM, a conservative 70-second window and Pacific-day guards/256 records/48 KiB UTF-16 state; it is not automatically Azure quota semantics. Obtain source-backed Azure RPM/TPM/window/token-estimation rules and actual deployed quotas. Extend only the owning quota boundary where needed with exact tests. Credit remains account-owned; health is backend-owned; quota is independently group-owned. Do not guess missing limits or invent RPD for Azure.
27. Verify atomic shared quota/credit admission, attempted-dispatch retention, cross-replica settlement/reaper, ETag conflicts/lost acknowledgements, health cooldown visibility and fail-closed storage outages with current-release isolated two-worker/replica tests. Use synthetic injected 429/5xx before output to verify cooldown/failover and no dispatch on local rejection; bounded genuine provider admission calls require fresh reserved program slots and exact evidence of both workers. Do not deliberately flood provider quota or call mocked faults live evidence. Unknown actual provider 429/5xx behavior remains explicitly unverified unless observed.
28. Whole-app autoscaling multiplies preserved non-Azure traffic too. Existing shared quota may be reused only if all required limits/semantics and safe capacity hold without unauthorized provider behavior changes. If global Table mode requires missing non-Azure group settings, do not fabricate them; prove an independently reviewed safe unchanged-provider operational admission alternative, or keep maximum one replica and report scale gate blocked. Static replica shares alone do not prove restart/scale-transition safety.
29. Prefer existing central observability: verify actual OTLP collector auth/network/retention and per-replica/process-lifetime counter/histogram aggregation with restart/reset/duplicate handling. Shared account/quota gauges and persisted debit counters are **nonadditive**. An honest alternative may use verified Azure platform aggregate request/CPU/memory/replica metrics plus canonical Table accounting and independently verified error/admission/latency visibility; label `/metrics` process-local, never scrape a load-balanced endpoint and claim total counters. Close alerts/runbooks and acceptance evidence before scale-out; new collector infrastructure needs concrete reviewed justification.

### Phase 6 — Bounded horizontal autoscaling and final acceptance

Depends on Phases 4–5, full candidate verification and independent scale packet review.

30. Azure Container Apps provides horizontal autoscaling; CPU/memory sizing is a static revision change, not vertical autoscaling. Add only required typed CPU/memory and HTTP/KEDA scaling parameters, preserve single-worker entrypoint, validate supported pairs and tie scaling concurrency to measured weighted memory admission. Default migration stays max1. Initial approved target is **min1/max3**, staged max2 before max3, with finite cooldown/scale-down stabilization, existing environment reuse and no scale-to-zero until cold-start/persistence acceptance is separately covered. Benchmark-derived values must be concrete in the reviewed packet.
31. Scale packet records static per-replica/three-replica cost estimates and a time-limited **30-minute** isolated scale exercise; stop/reduce back to one if unnecessary or unhealthy. Infrastructure spend is separate from USD 1 inference budget. Record region-specific estimates and operator's existing cost judgement; material unbounded infrastructure changes require renewed decision.
32. Use provider-blocked/injected upstream fixtures for sustained autoscaler load, not a paid inference loop. Verify actual 1→2→3 and 3→1 transitions, replica identities and no overlapping incompatible writers, aggregate memory envelope/readiness, shared admission and counters. Then bounded small real Azure admission/settlement calls (remaining fresh slots only) demonstrate shared state on at least two actual workers; inability to target/prove both is an open gate, not inferred success from configured maxReplicas.
33. During scale-down/restart, preserve SSE event bytes and terminate/drain correctly; no retry after output, duplicate debit, stale-seed replay or refund. Verify Table persistence, reservation cleanup/conservative recovery and real operational aggregation/alerts. Halt on unexplained 429/503, memory >70% under designed admission, false readiness, state drift or financial mismatch. Return to Table/one without resetting durable state if scale acceptance fails; reconcile ambiguous actions with a new packet.
34. Update canonical API/configuration/architecture/operations/observability/security and [requirements traceability](../../decisions/requirements-traceability.md), including actual completed scope and remaining unknowns. Preserve other providers and USER WORK. Validate relative links, final diff/whitespace/secrets and independently review deployed claims.
