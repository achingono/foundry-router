# Phase 4 Azure payload research

**Status: Research complete; implementation and large-payload acceptance remain Planned.** Sources were read on 2026-10-30. This note records public Microsoft contracts and local implementation constraints; it is not evidence of an Azure deployment or inference result. No Azure mutation, provider call, runtime/test edit, or benchmark was performed.

Scope is the configured Azure Foundry operations only: Azure OpenAI Responses, Azure OpenAI embeddings, Foundry-hosted Anthropic Messages, and Microsoft MAI image generation. Preserve other providers' existing request limits and behavior. This work is independent of the production memory/one-to-Table migration; payload work does not block that migration. See the [Phase 4 activity](activities.md#phase-4--azure-operation-payload-contract-and-simplest-safe-resource-architecture) and [current evidence](evidence.md).

## Bottom line

- Do **not** set a router wire-body limit to 512 MB on the basis of the Azure Responses image wording. Microsoft describes image-file and combined prompt/image *content* sizes; it does not define decimal MB versus MiB, say how inline Base64 characters are counted, or publish a general Responses JSON wire maximum.
- Azure documents PDF input separately: each file must be under 50 MB; the documented aggregate limit across files in a request is 50 MB. Embeddings are limited in **tokens and input count**, not a documented number of wire bytes.
- Microsoft Foundry's hosted Anthropic and MAI APIs have their own routes and payload shapes. No Azure-hosted Anthropic wire-byte maximum or MAI wire-byte maximum was found. In particular, do not import an Anthropic first-party API's separately stated 128 MB request limit as a Foundry-hosted Azure contract.
- The implementation currently has global 2 MiB default intake, configurable only up to 100,000,000 bytes, plus narrower provider-adapter restrictions and a full-body parser/estimator pipeline. Those are router limits, not upstream maxima. Raising the global setting alone would neither preserve other providers nor make peak memory safe.
- Smallest credible direction: benchmark the simplest bounded full-JSON parse/estimation path on a larger static container shape with bounded aggregate admission first. If measured memory amplification or concurrency makes it unsafe, compare a private quota-accounted ephemeral spool and incremental parse/rewrite path. Do not select or require the more complex path before measurement. Preserve existing conservative financial estimation and settlement; token/context semantic validation remains upstream-owned. Preserve existing caps after model resolution for non-Azure providers. Capacity rejection is appropriate for genuine concurrent resource contention only after one ordinary supported large request is shown to fit on an otherwise idle replica; it cannot disguise a permanently undersized per-request lane. Do not claim unbounded support where Azure's maximum wire size is unpublished.

## Content size is not serialized wire size

For an inline Base64 value containing `n` source bytes, the encoded payload takes `4 × ceil(n / 3)` ASCII bytes, before the data-URI prefix, JSON quotes/field names/commas, prompt text, other content, and any JSON escaping. JSON UTF-8 text and arbitrary request metadata add more wire bytes. URL and existing file-ID references have different request-wire costs from inline content. Consequently the same Azure content can have materially different HTTP body lengths.

As an illustration only (not an interpretation of Microsoft's undefined “MB”), Base64 for 512,000,000 bytes is 682,666,668 bytes; Base64 for 512 × 1,048,576 bytes is 715,827,884 bytes. Both require additional JSON bytes. The source does not select either unit basis or say whether its 512 MB check is on raw file bytes, decoded data, or encoded input. Keep these distinctions visible; do not turn the source phrase into `512 * 1024 * 1024` or `512_000_000` as a router cap. PDF's separate 50 MB file limit has the same Base64 expansion issue for inline PDFs.

An upstream context/token maximum is another independent axis. It does not establish a serialized-body limit, nor does a character or UTF-8-byte count establish a token count. Provider/model validation can still reject a request for context, shape, feature, image, or file reasons even when its wire body is small.

## Current router constraints and amplification points

Read-only inspection of the working tree on 2026-10-30 found:

- `Settings.max_request_body_bytes` in `src/foundry_router/config/__init__.py` defaults to 2,097,152 bytes and has a hard configuration maximum of 100,000,000 bytes. Both Responses and embeddings routes pass this one setting to `request_body` in `src/foundry_router/api/routes/openai.py`. This global limit can reject inline Azure images/PDFs before upstream dispatch, and is not an Azure limit.
- `src/foundry_router/api/common.py::request_body` checks declared `Content-Length`, then collects `request.stream()` into a `bytearray`. It subsequently makes a `bytes` copy, decodes the full body to a string, and calls the duplicate-key/depth/nonfinite/work-bounded JSON loader. The loader itself checks `len(text.encode())`, adding another full-body encoding pass/copy. A missing or misleading length therefore does not make current intake streaming-memory bounded.
- Responses cost estimation in `src/foundry_router/credit.py` walks Python objects and, for feature/tool/schema/media cases, projects `input`, `tools`, and `text` through `json.dumps(...).encode()`. The estimator has depth/character/serialized-byte guards and constructs copies; growing the request setting does not remove these post-parse bounds or the memory needed to materialize the parsed object and serialization. Embeddings estimation currently uses a conservative character-count divisor of 3, not an upstream tokenizer or an Azure token-limit check. These are local financial-estimation rules, not provider validation.
- The identity Azure adapter forwards the Responses body with a selected deployment. Foundry Anthropic uses the text translation in `src/foundry_router/api/adapters/opencode_anthropic.py`: incoming text is limited to 256 KiB, with up to 128 history items and 128 content parts per message. This is a local adapter bound, not evidence for a Foundry-hosted maximum. Its 4 MiB response-text bound concerns translated output, not incoming request bytes.
- `src/foundry_router/api/adapters/azure_mai.py` imposes `MAX_MAI_PROMPT_BYTES = 64 * 1024`, accepts one nonstream PNG-generation tool, and forces 1024×1024. That output size is within the documented MAI pixel rules. The 64 KiB UTF-8 prompt ceiling is router policy, not a byte limit published by MAI; the native prompt contract is token-based. The 64 KiB and 256 KiB bounds should not silently be represented as upstream maxima.
- This note covers **request intake**, not generated-response limits. The current MAI response path also applies `MAX_PNG_BYTES` and bounded PNG inspection; Microsoft specifies a PNG response and output pixel rules but no response-byte maximum. Treat that separate local output bound as its own review/acceptance question, not as evidence about MAI request wire size.
- Current ACA IaC in `infra/modules/containers/router.bicep` allocates 0.25 vCPU / 0.5 GiB per replica. This is the minimum Consumption shape, not evidence of capacity for large requests.

These limits are part of the present implementation state, not claims that the larger capability has been implemented or verified. Preserve unrelated working-tree changes; this research did not modify them.

## ACA ingress and finite resource envelope

Microsoft's [Container Apps ingress overview](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview), dated 2026-10-09, states “Request time out is 240 seconds.” The page retrieved for this review gives no HTTP request-body size limit, chunked-body limit, or ingress JSON parsing limit. Therefore the platform ingress body maximum is **unknown from the reviewed public source**, not unlimited. Treat the 240-second timeout as a separate time constraint and verify any additional front door/proxy path actually configured for the app before making an end-to-end support claim.

The [Consumption workload profile overview](https://learn.microsoft.com/en-us/azure/container-apps/workload-profiles-overview), dated 2025-11-04, publishes a per-replica range of 0.25–4 vCPU and 0.5–8 GiB. The reviewed [storage-mounts page](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts), dated 2026-10-13, documents temporary container/replica-scoped storage of 1 GiB at 0.25 vCPU, 2 GiB at 0.5 vCPU, 4 GiB at 1 vCPU, and 8 GiB above 1 vCPU. Storage is ephemeral (container-scoped data disappears on shutdown; replica-scoped data lasts for that replica). The current 0.25-vCPU shape therefore has a documented 1-GiB ephemeral-storage envelope, but no spool is currently configured and the available space is shared with other ephemeral use. These platform facts make a bounded spool a plausible design option, not a demonstrated capacity guarantee.

## Smallest safe implementation direction

Do not simply change the shared global byte setting to 512 MB (or a larger guessed value). Keep the implementation provider-local after server-side model/pool resolution and preserve all non-Azure defaults, adapter limits, prices, and behavior.

1. Authenticate before expensive body work. Count actual received bytes; never trust `Content-Length` as the sole enforcement mechanism. Benchmark the existing strict full-object parser and estimator on a resource shape sized for the required ordinary representations. If full-object parsing cannot meet the measured memory target, compare an incremental strict parser and rewrite path; do not mandate that complexity before the benchmark. Preserve duplicate-key, nonfinite-number, invalid-UTF-8, depth, and basic API-shape safeguards. Since the model may be late in chunked JSON, acquire Azure-eligible aggregate capacity before provider resolution, then resolve aliases/pools only from server configuration without trusting a caller-selected provider.
2. Before body intake, acquire a bounded, nonqueued **per-replica large-intake resource lease**. Reserve spool capacity incrementally as actual chunks arrive. Use a private per-request temporary file on ACA ephemeral storage (restricted permissions, no Azure Files/persistent prompt storage), or a proven streaming memory path if benchmarks show it safe. A single large-request lane plus bounded small-request concurrency prevents multiple admitted Azure-sized parses from multiplying memory. Release the lease and delete temporary bytes on every success, parse/estimation error, disconnect, cancellation, timeout, and shutdown path.
3. After parsing identifies the model, resolve aliases and candidate backends only from server configuration. Keep local provider handling limited to routing, authentication, safe syntax/resource handling, the request shapes the router already supports, and conservative financial estimation. Leave Azure semantic validity—including exact context/token limits, media validity beyond existing documented local safety handling, and model-specific input interpretation—to the provider. Do not recreate every upstream schema, tokenizer, or capability check. For non-Azure requests, preserve the existing configured intake/adapter policies and reject oversize bodies with their existing caller-size behavior; late model selection is not permission to change other providers. Do not reserve credit or start provider egress until authentication, parsing, routing, and conservative estimation succeed; never log content.
4. Preserve the existing conservative local financial estimator and configured pricing/media bounds. The chosen implementation may estimate from the parsed object if full-object parsing meets measured resource targets, or from incremental traversal if required by the benchmark. Change bounded traversal/serialization mechanics only as needed so obsolete local size/work limits do not reject ordinary supported Azure representations in the measured service envelope. An estimate is for reservation/accounting; it is not an exact provider token count, context validator, or reason to reject using Azure's semantic token maximum. Do not require a tokenizer, token-count API call, token-array input support, or provider-specific token prevalidation. Keep missing pricing or unestimable cost fail-closed and preserve MAI's fixed image liability and settlement rules.
5. Use the simplest measured-safe forwarding path. If the full-object path meets memory and aggregate-admission targets, retain it with a sufficiently large body allowance and avoid unnecessary new streaming infrastructure. If not, use a private spool and incremental upstream JSON writer/rewriter: Azure Responses changes the deployment field; Azure embeddings preserves the configured endpoint contract; Anthropic translates only the supported text subset; MAI emits the documented model/prompt/dimensions shape. Avoid full decoded image/PDF copies and unbounded whole-body buffering. Preserve request deadlines, cancellation, output/SSE boundaries, bounded retries, no retry/failover after meaningful streaming output, redaction, and existing credit settlement semantics.
6. Separate baseline size capability from overload behavior. On the selected final Linux resource pair, prove that an **ordinary single supported large request** fits through intake, parsing, conservative cost estimation, upstream rewrite, and a consuming mock when the replica is otherwise idle. Mandatory examples include near-512-MB documented image content plus Base64/JSON overhead, near-50-MB PDF input, normal Unicode/JSON escaping, model-last chunked bodies, and supported Anthropic/MAI text requests above the old local adapter byte caps. If one such ordinary request fails on an idle replica because of a spool, memory, parser-work, estimator, or deadline ceiling, that is an unresolved undersized design—not a successful `busy` rejection. Only after the idle case passes may finite aggregate admission return a clearly identified busy/overload response for genuine concurrent capacity contention. Use measured memory and scratch headroom and keep health/readiness responsive. Azure wire maxima not published by Microsoft remain unknown: this is a measured service envelope for ordinary supported representations, not an unlimited-size claim. If the smallest benchmarked safe ACA shape cannot support those representations, record the blocker for an explicit architecture decision rather than disguising a lower per-request cap as overload.

## Required regression and benchmark evidence

All large-body work can be tested with generated synthetic input and provider egress blocked; a paid near-maximum inference probe is neither needed nor implied.

- **Encoding/content boundaries:** generate inline image data URIs near both plausible 512 MB bases (decimal MB and MiB), below/at/above the documented strict-under boundary. Verify measured raw source bytes, Base64 bytes (`4 × ceil(n/3)`), full UTF-8 JSON bytes, and metadata separately. Include multiple images up to the 50-image count, mixed text/images, JSON escaping, non-ASCII text, tools/schema, long numeric spellings, and ordinary compact and whitespace-rich bodies. Do not commit giant fixtures; generate chunks on demand.
- **PDF/image/file paths:** generate format-valid representative PDF and PNG input fixtures (including large fixtures generated on demand), exercise near the documented content boundaries through a no-provider-egress intake path and a consuming mocked upstream, and include negative malformed PDF/PNG cases separately. Also test ID/URL references where supported, verify raw content/wire accounting, and ensure the estimator/logger never fetches, dereferences, or discloses remote content. Invalid or synthetic media must not be sent to paid providers or described as Azure acceptance evidence.
- **Embeddings:** verify intake, existing conservative financial-estimator parity, serialization, route forwarding, and faithful translation of a mocked upstream semantic error. The documented 8,192-token/input, 2,048-item, and 300,000-token aggregate limits remain research facts for the provider to enforce; do not add exact local token-boundary rejection tests or require a runtime tokenizer/token-count call.
- **Anthropic and MAI:** test supported text/Responses translations above the existing 256 KiB and 64 KiB local byte bounds through the consuming mock, while preserving server-side route selection and each adapter's actual supported input shape. Faithfully return mocked upstream context/semantic errors instead of adding local token/context validation. Keep media, editing, and streaming outside this size remediation unless separately authorized.
- **Routing/intake:** Azure and non-Azure models with `model` first/last, absent/false/valid `Content-Length`, split JSON strings/Base64 across arbitrary chunk boundaries, duplicate keys, invalid UTF-8, deep/large structures, slow uploads, disconnected clients and cancellation. Non-Azure inputs retain their old effective cap/response; Azure aliases cannot choose providers; no egress/debit/reservation occurs for intake failure.
- **Capacity/lifecycle:** saturate large lane and small lane; mix one near-boundary synthetic request with small traffic; exhaust spool quota; force disk-full/write errors, malformed JSON, estimator failure, upstream failure, cancellation, timeout, container restart, and concurrent cleanup. Prove leases and temp files are reclaimed exactly once and no prompt/image bytes reach logs or persistent storage.
- **Benchmark in the final Linux container/resource pair:** compare (a) full JSON parsing/estimation with a sufficiently large body allowance and bounded aggregate concurrency, versus (b) private quota-accounted ephemeral spooling plus incremental parse/rewrite if full parse is unsafe. Record the measured representation bytes, chosen strategy/resource pair, ACA ephemeral-space allocation and free headroom, peak process/container RSS, scratch bytes, CPU, event-loop/readiness latency, intake/forward time, and cleanup. Prove the idle single-request ordinary supported cases above end-to-end through the local parser, existing financial estimator, rewrite and consuming mock. Then separately test concurrent small+large pressure; a busy rejection is acceptable only in the contention cases after idle support is demonstrated. Include slow sender/receiver and repeated cycles. Require peak aggregate memory ≤70% of selected static container memory, responsive readiness, no OOM/leaks, and scratch cleanup. Near-boundary decimal/MiB fixtures are engineering headroom probes, not provider-acceptance claims. No paid giant-payload inference is required or authorized by this test plan.
- **Estimator parity and upstream error ownership:** compare the existing conservative estimates/reservations on ordinary fixtures for each relevant operation and configured Azure pricing/media profile. Demonstrate that mechanics changes remove obsolete local serialized-size/work/adapter byte failures for the measured supported cases without changing financial semantics. For provider semantic limits, use a consuming mock that returns a representative provider error and verify it is faithfully surfaced; do not locally prevalidate exact token/context limits. Keep missing/invalid prices distinct and preserve settlement.

Until these checks pass, report the router as **Partially implemented** for current bounded local payload handling and the measured Azure service-envelope design as **Planned**. A busy result does not pass the idle single-request size-capability case. Do not block the independently underway Table/one migration; do not report Azure wire limits as known where Microsoft has not published them, and do not claim support for all possible wire encodings or unbounded payloads.
