# G1 resume Activities

## Status: Implemented locally — live acceptance remains gated

## Step-By-Step Activities

1. **Read-only preparation of the partial run.** Treat the first apply as consumed. Never rerun its `apply`, recreate its original allocation, overwrite e/a/D bytes, retry cases 0–2, or reset the already consumed global guard. Read-only prepare captures exact e→a→D provenance, the original finish approval/link, case 0/1 pass receipts, case 2 consumed/ownership/HTTP/usage files, absence of a case-2 pass receipt, and no case-3/restart/DENY result markers. This preparation performs no ingress mutation, inference, restart, or append to original history.
2. **Pre-approval read-only reconciliation review only.** Before writing or reviewing an execution approval, recompute the reconciliation hash/input links and inspect case-2 HTTP 200/completed usage, original configured price/reserve, revision/process/image/settings/pinned-secret snapshot, canonical account debit/counter delta, and zero reservations/in-flight. This is packet preparation, not apply-time acceptance; it performs no original-history append, ingress mutation, provider request, or restart. Any drift rejects packet preparation. The apply runner MUST repeat every execution-time history, case/slot, current process, finance, configuration, revision/probe, topology, and ingress check only after its global continuation marker is durably consumed, so every such refusal reaches the one DENY attempt.
3. **Implement one narrow continuation boundary.** Add a single-use runner path and focused tests; do not add deployment/table/role/seed/pool mutation paths. The fresh packet binds hashes of the accepted case 0/1 pass receipts, exact original/finish histories, case-2 reconciliation, source, and a pinned DENY target (subscription, app, resource ID, and origin) copied from the original approved test packet; exact review must verify the receipts/financial chain and target. Execution first acquires nonblocking ownership locks and validates the prepared-packet bytes and exact approval. Once those gates pass, it exclusively consumes the durable global continuation marker **before rechecking any original history, prior receipt/debit/account chain, case-3 slot, process, finance, configuration, or live ingress state**. All such execution-time checks run inside a try/finally that attempts one final DENY on every exit. The separate DENY-consumed marker is written immediately before the single DENY PATCH—not at continuation start—and an ambiguous acknowledgement is never retried. If writing that secondary DENY journal fails after the global marker, still attempt one DENY under the global marker; if DENY is observed, stop without restart or an aggregate pass result. If the DENY marker already exists before the attempt, do not issue a second PATCH. If the global resume marker write fails before visibility or cannot be confirmed durable, the boundary was not crossed: do not dispatch or mutate ingress, preserve any visible marker, and require fresh review. If approval or ownership locks fail before the global continuation boundary, do not mutate concurrently—stop and require fresh review. Prove the original case-3 slot is still unstarted and accept no new allocation or budget. Preserve the existing Allow; there is no ingress-Allow operation in this path.
4. **Review and verify before execution.** Run focused and full checks, coverage ≥80%, Ruff lint/format, source/operator Mypy, relative-link checks, and contextual review. Independently review the actual fresh private continuation packet and exact code before execution. Carry forward one **30-minute total continuation deadline**, including cleanup headroom; the original bounded dispatch deadline (≤60 seconds), DENY mutation and propagation (≤60-second mutation, ≤120-second total HTTP-403 wait), 100-second quiet drain, a separate 180-second post-drain verification/marker window, and 180-second total restart observation. Every fsync-backed marker/result write and ambiguous global-marker durability confirmation is bounded to ≤15 seconds within the active budget; nested CLI, HTTP, snapshots, and cleanup obey the remaining global/phase budget. Before dispatch, reserve enough remaining time for the bounded DENY marker/write/403, drain, post-drain verification, restart, and cleanup tails even if dispatch consumes its full deadline. Approval is one case-3 dispatch within its original ≤64 input/≤128 output and slot reserve, one final DENY, quiet drain, and at most one current-revision restart. No paid retry, substitution, replay, or extra ingress write is permitted.
5. **Execute once and fence on every post-consumption outcome.** Before dispatch, exclusively persist the original case-3 consumption/ownership markers, perform the bounded readiness wait, then immediately take a final fresh all-revision/process/configuration/ingress/financial snapshot and require it to match the reconciled case-2 map and approved baseline. Do not place a wait or remote operation between that snapshot and HTTP dispatch. Any drift after the slot marker consumes the slot but dispatches nothing; the single DENY path still runs. Send only the original case 3 once. Verify terminal completion/usage, its original price/reserve, exact canonical-account settlement, and zero reservations. Append the absent case-2 passed receipt only from the verified reconciliation, then case 3. The post-approval continuation boundary guarantees exactly one final DENY attempt even if any pre-dispatch or paid-call guard fails; never repeat an ambiguous DENY. Require live 403. Only a fully reconciled four-case chain may proceed to the one restart.
6. **Prove the final state.** Under the proved DENY and quiet drain, compare same-process request counters and finances. Restart the current approved revision once, within the 180-second observation deadline. Require a changed real container/process, one healthy current worker, no old/unapproved workers, unchanged persisted balances/debit/recovery counters, zero reservations, and live 403. Append final results only after all checks.
7. **Stop and retain uncertainty on any failure.** Preserve consumed markers, actual response artifacts, financial liabilities, current fence, and Table rows. Do not retry case 3, apply another Allow/DENY, restart, refill, refund, reactivate an old revision, or continue production migration from a partial result. Any required action beyond this exact continuation needs another reviewed amendment.

- Focused tests explicitly prove: (a) post-marker history/slot/pre-dispatch refusal attempts one DENY, dispatches no case, and does not restart; (b) financial drift after the consumed case-3 marker and drift during the readiness wait both refuse before HTTP and DENY; (c) prior pass receipts with changed financial fields after approval are rejected and DENY before case 3; (d) global-marker failure after confirmed durability reaches DENY, while pre-visibility or durability-confirmation timeout performs no cloud mutation; (e) DENY-journal write failures before/after visibility still attempt exactly one DENY but stop without restart/pass; (f) a competing/pre-existing DENY marker causes no second PATCH; (g) fsync-backed marker/result writes receive the bounded remaining deadline; (h) dispatch timeout/failure retains liability, attempts one DENY, and never retries or restarts; (i) ambiguous DENY acknowledgement is never retried; (j) a new artifact directory cannot bypass the global resume marker and refuses before live preflight/mutation; (k) pre-boundary approval/lock failure performs no competing mutation; and (l) a slow post-drain snapshot is bounded separately and prevents consumption of the restart marker.
