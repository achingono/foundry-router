# Phase 10 Risk Register

## Risks

| ID | Risk | Impact | Mitigation | Status |
|---|---|---|---|---|
| R1 | Key Vault names are globally unique and capped at 24 characters. The current derived scheme already exceeds that cap for the `production` environment, so a deployment fails part-way through after other resources are created. | Deployment failure, orphaned resources | Length and shape decorators plus `assert` statements so validation fails first; document the constraint and keep the suffix scheme short | Open |
| R2 | Attaching to a pre-existing vault silently couples this workload to another team's data. A rotation, deletion or purge in that vault takes the router down. | Availability, cross-workload blast radius | Document the trade-off explicitly; namespace secrets with a configurable prefix; keep the per-workload vault available via `new` mode as the isolation-first option | Open |
| R3 | A newly provisioned vault currently defaults to access-policy authorisation, which is incompatible with the managed-identity RBAC design. | Secret resolution failure at runtime | Set `enableRbacAuthorization: true` for `new` mode and record the behaviour change; detect and document a mismatch rather than silently mutating an existing vault's model | Open |
| R4 | Registries that do not support Azure AD pull require a stored credential as a container-app secret, creating a long-lived credential with no expiry. | Credential exposure, rotation burden | Make managed-identity pull the documented default; treat secret mode as an explicit, reviewed exception with a named rotation owner | Open |
| R5 | The pull role assignment depends on the container app's identity, so on first deploy the app exists before `AcrPull` has propagated and may enter a transient `ImagePullBackOff` that looks like a crash loop. | Flaky first deployment, noisy alerts | Single-pass design with an explicit dependency; verify a clean first deploy into an empty resource group converges without manual retry, and document the expected transient state versus a true crash loop before labelling the template `Implemented` | Open |
| R6 | Environment-specific registry, vault, resource group or tenant names leak into version control. | Information disclosure, harder incident scoping | Gitignore `*.local.json`; placeholder-only committed parameter files; add a pre-commit or CI scan for subscription-specific names; review the diff for identifiers before commit | Open |
| R7 | The CI validation job inherits `existing` mode and then fails because the named resource is absent from its subscription. | Broken pipeline on unrelated changes | Keep committed parameter files in `new` mode; select `existing` mode only through gitignored overrides or workflow inputs | Open |
| R8 | Deriving the image reference by string concatenation instead of reading the registry's login server produces an incorrect pull target, especially for a registry with a custom suffix. | Image pull failure | Read the login server from the resource reference; assert the final composed reference is well-formed | Open |
| R9 | Removing `containerImageUri` silently breaks the deploy workflow, which overrides that parameter inline. | Failed or misconfigured deployment | Update `.github/workflows/deploy.yml` in the same change, replacing the inline `containerImageUri=` overrides with `registryServer`/`imageRepository`/`imageTag`; all six known call sites are inventoried in the Decisions section below | Open |
| R10 | A soft-deleted vault keeps its name reserved, so `new` mode recreation with the same name fails; conversely, attaching to an `existing` vault whose authorisation model differs from the template's assumption breaks secret resolution. | Failed redeploy, runtime secret failure | Document the soft-delete/purge collision path and the recovery steps; never mutate an existing vault's authorisation model — detect the mismatch at validation and document it instead | Open |
| R11 | The daily cap stops *all* ingestion when hit, so a cost incident becomes a monitoring blackout for the rest of the day. | Blindness during incidents, missed alerts | The 90%-of-cap alert is the real control and the cap is the backstop; document the cap-hit drill; size from measured baseline so routine traffic never approaches it | Open |
| R12 | The `Basic` plan charges per query scanned and limits alerting; a future log-alert or heavy-debugging need could cost more or fail outright. | Degraded incident response, surprise query charges | Default stands with the trade-off documented at the parameter; one-switch-per-week limit noted; explicit revert gate in the exit criteria | Open |
| R13 | Step 14 touches application code, expanding a phase otherwise confined to infrastructure. | Boundary creep, unreviewed behaviour change | Confine to telemetry-local log-level gating only; no routing/credit/forwarding/API change; focused tests plus the coverage bar; reviewer explicitly checks the diff emits strictly less | Open |
| R14 | `infra/parameters.prod.json` allows `maxReplicas: 2` while the app runs only in-memory credit, health and rate-limit stores; a scale-out splits reservations across replicas and overspends shared credit. Documentation describes Table Storage multi-replica state as verified, which hides the gap. | Credit oversubscription, misleading operational guidance | Cap `maxReplicas` at `1` by decorator and in every committed parameter file; set `activeRevisionsMode: 'Single'` explicitly; keep uvicorn single-worker; correct the documentation status; deliver storage provisioning and client wiring together in Phase 11. Residual: `maxReplicas` bounds one revision, so a rollout briefly overlaps two processes, and each revision restarts in-memory credit from configured balances; both are documented, not claimed closed | Open |

## Decisions (approved; no longer open)

- **D1 — Remove `containerImageUri` entirely.** The image reference is always derived, never free text. Rationale: every guard in this phase (validation, login-server read, suffix assert, scoped role assignments) depends on the reference matching the configured registry; a free-text override bypasses all of them and recreates the drift this phase exists to eliminate. Known callers to update in the same change: `infra/main.bicep:15,112`, `infra/parameters.staging.json:14`, `infra/parameters.prod.json:14`, `.github/workflows/deploy.yml:116,172`.
- **D2 — External registries are a first-class path, not an override.** Add an explicit `registryServer` parameter (validated: hostname only, no scheme or path) used only with secret-mode pull, combined with `imageRepository`/`imageTag`. This keeps the existing external-registry deploy flow working without a backdoor, and the Azure suffix assert applies only to Azure registries with managed-identity mode.
- **D3 — Default both modes to `new`.** It is the only mode that needs no pre-existing named resource and it keeps CI validation hermetic. Record the rationale in `infra/README.md`.
- **D4 — Accept the RBAC-authorisation switch for newly provisioned vaults.** The current access-policy vault cannot serve the Phase 08 managed-identity design. Never mutate an existing vault's authorisation model: detect a mismatch at validation and document it instead. Confirm no existing deployment needs a migration path before labelling `Implemented`.
- **D5 — Secret-name prefix is a parameter defaulting to an `appName`-derived value.** Safe default with zero configuration, and overridable to avoid collisions in shared vaults.
- **D6 — Pull-mode default is split by registry kind.** Deployments pulling from Azure registries default to managed identity; the workflow's external-registry deployments use secret mode with a named rotation owner recorded in `infra/README.md`.
- **D7 — Daily cap is parameterised, sized from baseline.** No guessed value is committed; the first-week measured baseline plus headroom sets it, with the sizing method recorded in `infra/README.md`. The 90% alert is deployed in-template; Advisor and budget alerts are operator runbook steps.
- **D8 — `ContainerAppConsoleLogs_CL` defaults to the `Basic` plan.** Rationale: router console output is high-volume and query-light, and per-query scan charges are expected to stay below the Analytics ingestion saving. Revert gate stands if query/alert needs emerge.
- **D9 — Hold pay-as-you-go and 30-day retention.** Retention stays inside the free window; commitment tiers wait for sustained ingestion approaching commitment thresholds, recorded as a future decision, not this phase.
- **D10 — Step-14 log reduction approved as a telemetry-local exception.** Uvicorn access logs off and candidate-array detail behind `WARNING`/debug; `FOUNDRY_LOG_LEVEL` stays `INFO`; no behaviour change outside emitted log volume.
- **D11 — Distributed state is not provisioned in this phase.** The Storage account, tables, data-plane role assignment and the app-side Table client form one contract (endpoint, table names, auth mode) and are only verifiable together, so they move as a unit to [Phase 11](../phase-11-distributed-state-wiring/index.md). This phase only adds the interim `maxReplicas <= 1` guard and corrects the documentation status.
